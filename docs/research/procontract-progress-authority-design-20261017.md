# ProContract 下一步：让可靠推进独立于会话结束

2026-10-17；设计提案，**尚未实现**。实现基线为 `7995605fa`；本轮证据检查点为 `fd7ee1d08`。本次仅检查已有源码与实验，未追加模型求解、评分或修改运行机制。

## 1. 核心判断

ProContract 应成为原生执行之上的薄层：**在原授权内，把工作变成可保存、可检查、可继续的进展，并严格区分这些进展与任务已经完成。**

它有两个不同职责。责任内核维护“谁能对哪个版本作什么承诺与结清”；运行层维护“下一步能否安全执行、产生什么可检查对象、反馈能否及时用于后续工作”。前一职责已经较明确；下一步应补全后一职责，并拆开两者之间不必要的耦合。

可概括为三条性质，但不能互相替代：

- **合法性**：没有授权、完整依据或正确对象，就不作对应状态转换。
- **可继续性**：存在获授权、有资源且有具体用途的下一步时，不因会话或整轮验收边界而失去执行机会。
- **有效性**：花费是否带来更好的程序、有效证明或有价值的反例，需要任务实验测量；日志数量、审查次数与 Support 数量都不能替代它。

V2 的持久责任与可替换执行，R2 的判别性实验与反例回放，Codex 版本的精确候选坐标与结清权，可以在这三个边界上组合。无需把每次实验升级为合同，也无需让一次模型会话承担整项任务的生命周期。

## 2. 这次实跑究竟说明了什么

| 证据 | 支持的结构性判断 | 尚不能推出 |
| --- | --- | --- |
| lightningcss、diffr 首轮均到 4 小时截止，只有 Issue，没有 Propose；配置无交付预留或催交通知 | 本配置依赖自然 turn completion 才进入正式反馈，长首轮可以耗尽机会 | ProContract 导致模型长首轮，或提前打断一定提高分数 |

| diffr 普通探针输出使 Docker 日志达到约 13.16 GB，需人工 SIGINT | 模型可见缓冲有界不等于实际作用、传输与存储有界 | 缩短工具回复或只限制 reviewer 就能解决 |
| mdbook 两次原评分因缺失声明依赖而无效 | 预检未覆盖评分方法的必要运行条件 | 候选分数低，或进程 exit 0 表示评测有效 |
| 部分私有 trace 达上限而无法完成观察 | 观察设施也有资源和完整性边界 | 常规交付、账本和评分一并无效，或原始请求审计完整 |

三个产物的观察分数高于所取 Vals 同题数值，但资格和条件不一致；没有同期对照，不能据此测出机制收益。实际没有后继求解，尤其不能声称本轮验证了“换执行者会提高质量”。完整数字及限制见 [评测检查点](procontract-programbench-checkpoint-20261017.md)。

前一版设计中的逐项回执、局部审查、PTY 对话、冻结计算和持久化计算授权已经实现。这次问题位于它们外围：**已有的局部能力没有覆盖普通执行路径，也没有及时接入仍在进行的求解。**

## 3. 保持少量独立对象，避免增加总状态机

以下是现有记录的职责边界，不是五套新服务或数据库：

| 对象 | 必须回答的问题 | 不能被当作 |
| --- | --- | --- |
| 原任务与授权 | 原目标、权限、不可续期的资源边界是什么？ | 当前模型的计划或自报完成 |
| 冻结产物 | 哪一组确定字节被保存或提交？ | 所有义务已满足 |
| 观察与判断 | 哪个方法在什么环境检查了哪个对象，得到什么范围的结论？ | 普遍正确性或新权限 |
| 执行生命周期 | 哪个动作启动、结束、取消或仍然未知？ | 候选质量或验收结果 |
| 合同状态 | 当前正式候选获得什么支持，谁作了结清？ | 当前进程状态或所有探索历史 |

继续使用现有 kernel/store、working evidence、controller、Codex adapter。读模型应组合展示这些事实：例如“执行已因预算停止；最后快照可用；检查完成 12 项、剩余 3 项；尚未 Support”。不再让一个 phase 字符串同时回答它们。历史的 phase=working 仍是历史记录，不应被覆写为任务已成功。

记录可以持续追加；对真假的判断必须允许撤回。保留了一条反例并不意味着它仍适用于最新版本；没有新反例也不表示未知区域已覆盖。

判断时分别计算三个问题：当前获授权且资源足够的动作能否执行；观察是否足以支持某个局部结论；全合同是否满足既定验收条件。第一个问题不要求第三个已经可保证为真。明确的原任务授权、具体用途和剩余能力可以支持探索或补证，不能把 `Defeat` 设为一切继续工作的唯一入口；模型声称“值得继续”也不能自行获得新授权。

## 4. 最小语义变化：发布进展不必结束执行

当前 [runtime.rs](../../codex-rs/ext/pro-contract/src/controller/runtime.rs) 在 `turn_stopped` 捕获，`thread_idle(Completed)` 提交 delivery，再由 `promote` 进入正式验证。[内核](../../codex-rs/pro-contract/src/transition.rs) 的 `Propose` 增加 generation 并清除已有 Support。两者说明，直接周期性伪造 Completed 或 Propose 都会混淆含义。

增加一个宿主能力 `publish_progress`，复用现有 capture、blob、实验日志与证据读取。它发布一个可被局部检查的对象，同一原生 turn 可以继续。模型可提出希望核验的主张；是否执行哪项检查及其授权由宿主决定。

概念接口如下，字段名不是已冻结的公共 API：

```text
publish_progress(request_id, optional_review_targets, note)
  -> snapshot_id | explicit_capture_blocker

ProgressSnapshot = {
  intake, execution_epoch, publication_seq,
  subject_hash, capture_policy_hash, capture_boundary, reason
}

Assessment = {
  snapshot_id, scope, method_digest, inputs_digest, environment_digest,
  receipts, local_judgments, gaps, visibility
}
```

大部分字段已有对应物。`note` 和 review targets 是不可信的工作建议，不是完成证明。首版只增加一种发布入口，扩展现有 `contract_read_evidence` 的归档与分页；不增加计划器、多个“进度评审角色”或完整命题图数据库。

### 4.1 捕获必须有真实的一致性边界

宿主在本任务工具调度安全点阻止新的相关写入，确认已派生的写入者停止或暂停后，按原 capture policy 生成不可变对象并提交回执，再恢复执行。也可由有对应保证的适配器使用原子文件系统快照。不能仅因当前工具已经返回，就认为其后台子进程已停止。

现有 capture 的两次扫描能够发现一部分变化，不能单独证明并发多文件捕获是原子的。哈希标识所捕获的内容，也不能证明内容在业务上可构建。无法建立捕获边界时返回明确阻塞，保留上次有效快照，不无限等待，也不把混合版本称为一致交付。首版限于宿主能管理全部相关写入者的本地工作区。

发布不要求模型先自然结束，不把任务判成完成；仍可能需要一个短的、有限的写入屏障。这是数据一致性要求，不是新的研究阶段。

### 4.2 进展检查与正式验收分开

进展快照先进入工作证据日志。局部检查可发现反例、验证引理或确认附件可读，不必每次启动整个 suite 或完整 reviewer。评估旧快照 S1 时，执行者可以继续修改工作区；回执必须一直绑定 S1。对 S1 的结论不能直接 Support 或 Defeat 正式候选 S2。

正式交付仍可兼容当前自然 handoff，并对选定冻结对象执行 `Propose` 和完整验收。已完成的检查只有在 subject、scope、方法、环境、依据及当前 policy 全部匹配时才可复用；新 generation 仍需当前坐标的明确判断，不能搬运旧 certificate。首版对不同 subject 保守失效，不推断文件未变就意味着数学假设或程序依赖未变。

进展快照使用自己的 publication_seq，不能冒充 kernel generation。当前 `work::frontier` 按正式 generation 折叠，新进展记录先单列；否则迟到的 S1 结果可能错误关闭 S2 的反例。界面和返回消息同时提供“被检查对象”和“当前对象”。

### 4.3 调度只决定有限工作，不判断研究价值的真伪

优先利用已有公开反例、模型请求核验的关键主张、方法能力缺口和接近原截止时间的交付需要。具体实验与推导仍由原生求解者选择。没有可检查的新对象时，不机械地产生一次完整审查。

同一产物可以接受新的检查方法或输入，得到实质新证据；产物哈希不变不等于没有研究进展。去重需匹配对象、范围、方法、输入和环境，不能只匹配 subject。反之，改动笔记或增长日志也不自动证明值得继续。重复失败且条件未变时停止该路径，是分配策略；不能将某个固定重试次数提升为普遍研究规律。

首版每任务最多一个活动评估和一个待评估快照；相同绑定的重复请求复用已有记录。待评估位置可以更新为较新快照，但保留发布历史，不反复取消已接近完成的评估造成饥饿。发布次数、捕获容量和评估预算均有限。反馈投递到原生会话安全点，带稳定 ID 和持久确认；适配器若不支持去重确认，崩溃后的投递保持未知并由归档供读取，不能盲目重复注入。读取已提交反馈不重跑检查。

宿主可在准入时确定有限的“最晚请求发布”边界，为捕获和退出保留机会；这是一项可测调度策略，不是合同语义或“每十分钟打断”的普适规则。强制截止只负责停止作用和交付已保留对象，不能补写自然完成。不能保证每次长推理都在截止前产生可发布产物。

## 5. 授权分配：允许有限进展，不承诺必然完成验收

当前 [prepare_successor](../../codex-rs/ext/pro-contract/src/controller/runtime/succession.rs) 将 check timeout、reviewer timeout 与 60 秒相加；[Budget::reserve](../../codex-rs/ext/pro-contract/src/controller/succession_budget.rs) 从剩余时间扣除此总额后才允许执行。需要拆开的是三个量：动作的硬上限、原授权的实际余量、为某个下一步选择的预算。

延用持久化 reservation/CAS 和 inspection grant 的经验，让所有角色的动作引用原始授权，派生有限分配：

```text
ActionAllocation = {
  parent_grant, action_id, owner_epoch, purpose,
  deadline <= parent_deadline, enforceable_resource_caps
}

action_deadline = min(parent_deadline - required_cleanup_margin,
                      now + chosen_slice, now + configured_action_ceiling)
```

这只是截止上界；准入还要求正的可用时间、用途所需的最小执行能力、原剩余计数和可靠的生命周期管理。所有准备、检查、审查、捕获与退出都必须受对应原授权约束，不能因启动时间不同重新获得完整时限。外部正式评分若有单独授权，继续单列，不能挪给求解者。

墙钟时间不按并发动作的持续时间相加；累计 CPU、token、存储或调用次数需要各自的计量与总量限制。未可靠测量的账单不伪装成精确预算。重启保留原 deadline；时钟异常保守拒绝新动作。已派发或未知的调用额度不退款，重复发布不能刷新计算次数。未耗尽的墙钟余量仍属于同一个原截止时间，不是续期。

mdbook 的已知反例可以形成“有界修复 → 捕获 → 有界回放”的下一步，即使剩余 3,597 秒不足以保证一轮 4,260 秒的最坏验收。如果最终只能完成局部检查，就交付未完整验收的修复产物，明确未决项。反过来，余量连可靠执行、捕获与退出都不够时，应停止，不能仅因余量大于零就开启新会话。

上次检查耗时可以作为分配策略的观测，不能替代硬上限或保证审查完成。为全局验收预留多少是可替换策略；合法性由原授权、动作上限及验收条件分别保证。任务也可能要求先验收再产生外部作用，此时预算不足只能保留工作，不能执行该外部作用。

同一执行者能使用反馈时优先继续；更换执行者只处理上下文、退出或明确的工作分配需要。`Defeat` 不应天然意味着必须新开一个模型会话；更换会话也不能产生新 Issue、新权限或新预算。

## 6. 所有真实作用都要经过宿主边界

[execution.rs](../../codex-rs/ext/pro-contract/src/execution.rs) 已为检查/inspection 提供起止回执、捕获上限及退出处理；普通执行者通过 native unified-exec/exec-server，未获得同等的整条路径资源保证。应复用边界语义，在原生执行层落实，而不是把普通 shell 绕行进另一套模型工具循环。

| 层面 | 要约束与记录的内容 |
| --- | --- |
| 进程与作用 | 真实进程/会话身份、后代、总执行截止、CPU/内存/pids、终止与退出确认 |
| 原始输出传输 | 编码前累计字节、传输队列、限额停止原因；保留控制与终态消息 |
| 捕获与存储 | 每动作和每任务的日志总量、Docker 日志、trace、可写工作区与 scratch；截断范围 |
| 模型呈现 | 头尾片段、摘要、分页与 omission 标记；不以呈现长度代替前三层 |

动作返回 session_id 或 yield 只是一次交互结束，不能重置后台进程的 deadline 或输出计数。多次 read/poll、重连、编码膨胀及日志副本也必须计入实际存储边界。stdout 上限不能阻止直接写文件，必须由工作区/临时卷配额或等价能力覆盖该作用；做不到的 profile 不能宣称存储有界。

输出硬上限应在生产端附近执行，保留协议 framing 和终态消息，有限终止该动作，确认其所属进程组退出并给模型资源回执。不能截断 JSON-RPC transport 本身而破坏整个会话。Docker 日志轮转是独立的容量防线，不能代替进程输出上限；截断后也不能声称完整捕获。需计入缓冲及清理允许的最大超量。

完整原始 trace 可选且受限；必要的授权、动作与交付回执须有独立的容量预留和失败语义。可选 trace 用尽只使对应观察变为不完整；必要回执无法持久化时禁止据此验收或继续依赖其效果。不能为“审计完整”无限占盘，也不能静默删掉必需证据后仍报完整。

启动前保留 action identity 与 reservation，效果发生后记录结果。崩溃后若只剩 start，状态就是未知；先按原身份核对、停止或恢复读取，不盲目重发。远程不可逆动作只有在适配器提供可验证幂等键/查询语义并具备原授权时才可恢复；本地进程的成功处理不构成任意外部事务 exactly-once 保证。

宿主统一这些不变量与回执语义，底层可以有不同实现。无需把 Docker、PTY、模型推理与远程 API 强行塞进一个通用 `run()`。

## 7. 方法可用性、候选真假与信息独立性

每项证据都有方法前提。将现有环境/方法身份扩展为有范围的 readiness 回执：所需依赖、协议能力、集合/分母、输入解析与最小正常路径是否可用。它回答“能否做这类观察”，不回答“候选是否正确”。

- ProgramBench 的依赖安装、导入和 collection 检查由评测适配层在付费求解准入前完成，使用相同冻结环境；不把 bs4 等包名写进责任内核。必要时使用允许的已知基准产物校准，单列预检开销。隐藏断言、测试内容与反馈留在评分域，求解者只获方法是否可用的公开状态。
- jplot 的正常握手与输出必须实际可达，help 成功不足以证明终端取证可用。方法代码、输入、环境变化后需要相应重新校准。
- 数学任务核对冻结证据是否可解析、有限检查是否能执行，并保持主定理、关键引理、数值观察及附件缺口的范围。有限数值支持不能升格为全称证明。

Readiness 也会失效。环境变化或运行期依赖故障形成方法阻塞，不能转为候选反例；方法恢复须绑定新的环境身份并保留原失败。若改变判据而非仅恢复既有能力，遵循原合同的显式修订机制，不能为了过关修改门槛。

探索方法可以随着研究变化，冻结验收条款不应冻结所有探索。新增 probe 可先作为带身份的工作证据；成为正式验收依据需满足既定 policy，或按授权修订 policy。这样既能吸收执行者发现的有效方法，也避免自造自测直接结清。

更早、更频繁的反馈还会改变证据的独立性。已被用于修改或选择候选的测试/审查进入该候选的可及信息范围，重复使用不能包装成新的独立 holdout。现有内核 `Reach` 边界应保留，进展反馈不得自动升级为 Beyond；官方评测也不能变成在线优化 oracle。同模型家族的两次审查仍可能有共同盲点。

COLT 历史实验已产生获独立解析审查认可的主证明和扩展，但内部附件核验失败；它不是整项研究没有成果。下一步应让主证明反例或缺口更早进入研究，而不是只在终局增加 reviewer。仍需分别报告已核验的命题、有限证据、未决问题和新颖性限制。旧题用于诊断，不作为新盲测收益。

## 8. 落地顺序、可证伪验证与迁移范围

先把新增行为做成小的完整闭环，保持责任内核接口不变：

| 顺序 | 最小改动与位置 | 必须观察到的结果 |
| --- | --- | --- |
| 1 | native exec/exec-server 及 runner 的资源配置；评测适配器 readiness | 高频输出、后台子进程、缺失依赖不会再需要人工救场或产生有效假分数；同一模型会话能收到明确回执 |
| 2 | controller 的 publish/capture 与 archive；native 安全点适配 | 同一长 turn 发布 S1、收到其局部反馈、继续产生 S2；无需先伪造 Completed 或改变合同 generation |
| 3 | succession/inspection/worker 的原授权派生分配；调整旧准入公式 | 余量不足整轮最坏验收但足够一项有用工作时可以继续；截止、计数及未知效果约束不松动 |
| 4 | 将调度做成小策略函数，以持久记录为输入 | 能选择下一步检查或修复，解释为何停止；不复制模型循环，不引入通用工作流 DSL |

第 2、3 项应一起完成“同会话发布—有限检查—反馈—修复—再发布”的纵向集成验证，再测求解质量。资源防护与资格修复先于新的长时间实跑。限制值和调度参数在实验前冻结；本提案不把某个未测比例写成普适默认。

首批有意义的机制验证：

1. **真实普通执行路径**：小限额的持续输出、写文件和派生子进程，穿过 exec-server 与 Docker；核对实际磁盘/队列上界、退出确认、协议可用性及原会话继续工作，不只测字符串截断 helper。
2. **同 turn 反馈**：脚本 provider 先提交错误公开行为、发布 S1、读到完整反例、修复并发布 S2；只在最后自然交付时 Propose。旧 S1 的迟到评估不能改变 S2 的验收。
3. **一致捕获**：并发跨文件写入、后台写入和捕获超时；无法取得屏障时必须保留失败，不把不一致产物当成成功快照。
4. **有限余量**：模拟 mdbook 的 3,597/4,260 秒关系；允许可执行的有限修复，完整验收不足时保留明确缺口。覆盖余量不足退出、重复 reserve、重启、时钟后退及取消。
5. **恢复语义**：在 reservation、dispatch、capture、receipt、反馈投递各边界注入崩溃，核对没有额外 Issue、重复效果、额度续期、隐式 Support 或自动 Discharge。
6. **证据域故障**：缺失声明依赖、集合错误、无效分母、trace 写满与必需日志写满分别落到正确资格；证明主项已检查与附件未读可以并存。

机制通过后，再预先选择未用于调参的实例，做同模型/effort/总授权的原生 Codex 对照。所有实验臂共享基本资源保护和评测能力修复，否则测到的可能只是基础设施差异。最小消融依次比较原生、现有 ProContract、增加进展发布、再增加预算策略；明确各角色与评估计入总用量。样本允许时重复并报告方差，不以最好一次替换原始尝试。

除官方质量、完全解决率、成本与人工干预外，记录首次可行动反馈时间、反馈后剩余授权、被实际使用的反例、无新增观察的重复消耗、检查开销及未核验交付。中间指标用于解释结果，不替代最终质量。对照 Vals 需另行匹配其预算、工具限制、实现约束与评测身份，并使用同一任务集；目前三题结果不能充当榜单结论。

迁移先沿用现有模块与实验日志，新增 schema 显式版本化；旧记录按原语义读取，不补造 publication、原始输出或 readiness。分阶段替换旧的“完成后才能检查”路径和整轮最大值预留，避免长期并存两套预算真相。核心 `Issue/Propose/Support/Defeat/Discharge` 无需增加新命令。

当前最合理的载体仍是已有 Codex 集成：需要的修改在原生执行、安全点和证据持久化边界，换 harness 本身不能消除这些问题。OpenCode 或 Pi 的适配是否更好，要看能否提供相同的身份、冻结、取消、持久化及资源保证；本次没有跨 harness 实验，不作普遍优胜结论。

本设计对程序、理论研究、数据分析与多步骤工具任务共享的是授权、对象、观察和作用边界。域内的证明方法、覆盖标准与外部事务恢复仍需相应适配。能争取的是**在已声明能力和故障模型内，作用有界、失败明确、进展不丢、反馈可用**；不能由一个通用协议保证任意 long-horizon 任务都成功或绝对零机械错误。
