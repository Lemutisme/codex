# 从真实运行中的停止原因改进执行与策略接口

## 问题与改动

`4fedcd84a` 的 ProgramBench 验证中，handlr 为 671/722（92.94%），pls 为
245/331（74.02%），bat 在读取随题图片后被文本网关终止。这些原始结果保留在
`/data/ProContract/programbench-continuation-20261022`，没有恢复求解或改写评分。

这次修复涉及四个通用接口：

1. **可用能力必须与实际传输相容。** 文本 benchmark 入口关闭原生看图工具。
   如果其他工具仍产生非文本输出，网关明确报告该部分观察未送达，保留文本和
   审计摘要，继续使用同一请求预算。它不会把图片放行，也不会默默当作完整结果。
2. **协议表达合法动作本身。** continuation 使用带标签的选择：rest 只有原因；
   resume/successor 有工作目标和下一步。schema 与解析器采用同样的分支结构，
   不再让模型从两个独立字段中猜测隐藏的组合约束。重复目标 ID 归一化；未授权
   动作或义务仍拒绝。
3. **意图、执行、观察分别保留并关联。** 选择事件的 hash 关联实际 successor
   预留/返回、同线程提交确认，以及精确 turn 对应的交付。策略同时看到当前评估
   和 executor 的工具能力。返回成功不代表修复成功；没有收据也不代表没有执行。
4. **一次执行请求的上下文与指令一起交付。** 新的真实选择测试暴露出 native
   automatic turn 将附加上下文直接用于首次采样、却把执行指令放进待处理队列。
   较长 worker packet 因此先产生一个回答，再为迟到的指令多采样一次。修复将
   上下文与指令共同排队，由首次采样一并取得；保留自动输入来源和 mailbox 语义。

纯 kernel 与 store 未改动。未增加重试次数、固定工作流、评分门槛或任务时间限制。
真正的原始授权和资源限制继续生效，历史选择保持原样读取。

## 策略层的改进

pls 的内部差分从 111/123 提升到 120/123，但官方失败仍集中在配置和排版；
handlr 的内部差分从 73/76 提升到 75/76，官方 51 个失败中 31 个属于自动补全。
已观察反例的修复和尚未覆盖范围的探索，需要由策略共同考虑。

`continuation.md` 和 `work_method.md` 因此要求比较当前残余问题、未观察范围、
实际执行结果和剩余资源，再选择下一项工作。缺失历史过程证明不能靠重复完整审查
补齐。这里没有把某个案例的功能类别、成功分数或循环次数写入 harness。

## 本质与边界

核心改进是让策略有条件根据真实变化决策：它可以看到某个选择确实得到执行、
产生了哪个产物，而当前评估仍指出什么问题。能力、授权、执行事实和结果判断
各有来源，不靠一段笼统的“已尝试”或“缺证据”概括。

这仍不是普遍有效的长任务策略。完整执行历史的可检索证明、初始准备与最终审查的
调度解耦仍未解决；现有 review 也可能继续花费过多精力讨论无法取得的历史证据。
本次没有降低接受标准来制造 Support，也不以内部 Support 否定有效外部分数。

后续自动进化可复用相同区分：保留原始 trajectory，提出有明确归属的修改，运行
针对性回归，再冻结独立尝试比较产物质量、资源消耗与机械失败。一次测试通过或
一次高分都不是自动推广的充分证据。当前未启用自动修改/推广的 RSI coordinator。
